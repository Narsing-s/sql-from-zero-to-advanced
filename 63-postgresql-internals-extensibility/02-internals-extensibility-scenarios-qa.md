# Advanced PostgreSQL Internals, Extensibility & Failure Scenarios — Q&A

Use this production answer structure: **Impact → Scope → Evidence → Safe mitigation → Root cause → Permanent fix → Validation → Prevention.**

## 1. A PostgreSQL 18 MERGE unexpectedly updates rows instead of inserting them. What do you check?
Check the source-to-target join, candidate-row classification, and WHEN clause order. PostgreSQL evaluates WHEN clauses in order and executes the first true clause, so a broad MATCHED condition can capture rows before a narrower condition.

## 2. A MERGE works in staging but behaves differently in production.
Compare source duplicates, constraints, statistics, triggers, permissions, data distribution, and exact SQL/version. Do not assume plan differences alone explain semantic differences; verify the actual source and target data.

## 3. A prepared statement is fast for one customer and slow for another.
Suspect parameter-sensitive plan behavior. Compare custom and generic plans, parameter distribution, row estimates, and EXPLAIN (ANALYZE, BUFFERS). Use an evidence-based plan-cache strategy.

## 4. A query became slow after a statistics refresh.
Compare old/new plans and estimates, especially joins, selectivity, partition pruning, and index choices. Validate whether the new statistics better represent current data or whether a plan regression occurred.

## 5. A production incident shows excessive temporary files.
Identify the responsible query from logs/statistics, inspect Sort/Hash nodes and work_mem pressure, and check whether a query rewrite or index can reduce the operation. Do not blindly increase work_mem globally.

## 6. A database reports high memory use after an extension deployment.
Inspect backend memory, extension code paths, memory-context behavior, and connection lifetime. Reproduce under controlled load and compare memory growth per session. Roll back or disable the extension if it threatens stability.

## 7. An extension crashes the server during a rare query.
Treat it as a server-impacting software defect. Capture logs/core diagnostics, isolate the extension and query, prevent repeated triggering, and test a fixed extension build against the exact PostgreSQL version.

## 8. An extension loses state after a crash.
Review whether persistent changes were correctly represented in WAL and recovery hooks. Validate crash/restart behavior repeatedly; successful normal execution is not evidence of crash safety.

## 9. An FDW query transfers millions of rows over the network.
Inspect the remote SQL generated by the FDW and determine whether predicates, projections, joins, or aggregates can be pushed down safely. Measure network volume before and after.

## 10. FDW pushdown returns different results from local SQL.
Check remote/local collation, NULL behavior, type coercion, time zones, functions, and operator semantics. Disable the suspect pushdown until semantic equivalence is proven.

## 11. A foreign server is intermittently unavailable.
Separate remote dependency failures from local PostgreSQL failures. Measure connection latency, remote error rates, pool usage, timeout behavior, and retry storms. Apply bounded retries and circuit-breaking at the appropriate integration layer.

## 12. A custom data type causes incorrect ORDER BY results.
Inspect comparison operators, sort semantics, collation assumptions, and operator classes. Verify transitivity, equality consistency, and index behavior with adversarial test data.

## 13. An index returns incorrect results after introducing a custom operator class.
Treat this as a correctness incident. Compare indexed and sequential results, validate operator-class support functions, and remove the unsafe index/extension combination until correctness is established.

## 14. A view suddenly changes behavior after adding a rule.
Inspect the rewrite rules and the rewritten query behavior. Determine whether the rule introduces additional actions or changes command semantics. Prefer a trigger or explicit application workflow if the rule is unnecessarily complex.

## 15. A developer proposes using rules for an audit system.
Compare rules with triggers and explicit audit tables. If row-level change context is required, triggers may provide a simpler execution model. Document the choice and test multi-action statements.

## 16. A trigger and a rule both modify the same data.
Map the complete rewrite and execution sequence. Identify recursion, duplicate writes, ordering assumptions, and transaction effects before changing either mechanism.

## 17. A logical replication subscriber stops after publisher failover.
Verify the standby was configured for logical-slot synchronization, the relevant slots were synchronized before promotion, and the subscriber is connecting to the promoted primary with the expected slot state.

## 18. A logical replication slot is missing on the promoted standby.
Do not recreate it blindly. Determine whether slot synchronization was enabled, whether the slot had caught up, and what WAL/change position the subscriber requires. Follow the documented failover procedure.

## 19. The subscriber is behind during failover.
Confirm the standby/subscriber ordering requirement and inspect replication slot positions and replay/apply progress. Avoid promoting a node that cannot safely continue the logical stream unless the recovery plan explicitly handles the gap.

## 20. Logical replication works but generated columns are wrong on the subscriber.
Check PostgreSQL 18 publication settings, column lists, and generated-column replication behavior. Verify whether the subscriber is expected to compute or receive generated values.

## 21. A PL/Python function causes latency spikes.
Measure execution time, calls, concurrency, external work, memory use, and language-runtime behavior. Move expensive work outside the database when appropriate and keep database-side functions deterministic and bounded.

## 22. A procedural-language function becomes a security risk.
Review ownership, privileges, trusted/untrusted language status, SECURITY DEFINER usage, search_path, dynamic SQL, and access to filesystem/network capabilities. Minimize privileges and schema exposure.

## 23. A new procedural language fails during CREATE FUNCTION.
Inspect language installation, handler, validator, permissions, shared-library availability, and PostgreSQL version compatibility. Treat the validator/handler as part of the extension deployment.

## 24. An SPI-based extension leaks memory under repeated calls.
Capture memory-context statistics and reproduce with repeated transactions. Identify allocations that outlive their intended context and move them into the correct context or explicitly release them.

## 25. An extension works in psql but fails through an application.
Compare protocol usage, prepared statements, transaction boundaries, session settings, search_path, role, and connection-pool behavior. Reproduce using the application's exact session characteristics.

## 26. A custom scan provider gives different results from the normal planner.
Disable the provider for the affected workload, compare result sets, and build deterministic regression tests. Correctness has priority over the optimization.

## 27. A custom table access method corrupts data after restart.
Stop further writes if necessary, preserve evidence, and investigate WAL/recovery integration, page format, checksums, and crash-recovery behavior. Restore from a known-good backup if integrity is uncertain.

## 28. A custom table access method is fast but causes huge WAL volume.
Measure WAL records and page churn, then determine whether the access method's persistence strategy is generating unnecessary WAL. Any reduction must preserve crash safety and replication requirements.

## 29. An application reports serialization failures after a query change.
Capture SQLSTATE, transaction boundaries, isolation level, lock graph, and retry behavior. Add bounded transaction retries only for retryable errors and keep transactions short.

## 30. A deadlock appears after adding an audit trigger.
Build a two-session reproduction, inspect lock ordering, and identify whether the trigger introduces cross-table locks. Make lock acquisition order consistent or redesign the audit path.

## 31. A query's plan changes after a PostgreSQL major upgrade.
Compare statistics, planner settings, indexes, extensions, SQL behavior, and EXPLAIN output before/after. Test representative production queries before upgrading the full fleet.

## 32. A catalog query suddenly fails after an upgrade.
Prefer supported system views or documented catalogs over undocumented assumptions. Compare the new catalog schema and update tooling to the supported interface.

## 33. An application depends on information_schema but needs PostgreSQL-specific metadata.
Use information_schema for portable metadata and PostgreSQL catalogs/views for PostgreSQL-specific diagnostics. Isolate vendor-specific SQL in a compatibility layer.

## 34. A client sees unexpected protocol errors after a driver upgrade.
Capture server logs and protocol-level error details, compare driver versions, prepared-statement behavior, SSL/authentication negotiation, and connection startup parameters.

## 35. Authentication works manually but fails through the pool.
Compare role, database, SSL mode, authentication method, startup parameters, and pool reuse. Check whether stale connections or different connection credentials are involved.

## 36. A pool causes many idle-in-transaction sessions.
Inspect application transaction handling and pool configuration. Terminate unsafe sessions only after understanding application impact; fix transaction lifecycle and enforce reasonable idle-in-transaction timeouts where appropriate.

## 37. A rule causes an UPDATE to affect more rows than expected.
Inspect the rewrite rule definition and generated actions. Reproduce with a small dataset and compare against a trigger-based equivalent before changing production behavior.

## 38. WAL grows rapidly during a batch job.
Identify the source of WAL: updates, deletes, index changes, replication, logical slots, or long-running transactions. Check replication slot retention and transaction age before changing WAL settings.

## 39. A logical decoding consumer stops while WAL continues accumulating.
Check consumer health, replication slot state, confirmed flush position, network connectivity, and decoder errors. Restore consumer progress or safely drop the slot only after determining whether retained changes are still required.

## 40. A production extension upgrade passes unit tests but fails during rollback.
Test upgrade, downgrade, crash recovery, replication, concurrent access, and existing-object compatibility. Treat extension versioning and rollback as first-class production paths rather than release-day surprises.

## Final interview drill
For any advanced PostgreSQL incident, do not jump directly to a configuration change. First establish **what changed, who is affected, what evidence proves the failure mode, what mitigation is reversible, and how you will validate recovery**.
