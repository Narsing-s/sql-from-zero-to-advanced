# Complete SQL Theory — Core to Expert PostgreSQL\n\nThis document is the single theory reference for the repository. It closes common gaps between SQL syntax, database theory, PostgreSQL internals, production engineering, analytics and distributed systems.\n\nLearning rule: Definition -> Why -> Mental model -> Syntax -> Example -> Edge cases -> Performance -> Security -> Concurrency -> Production troubleshooting.\n\n# 1. SQL and relational foundations\nSQL (Structured Query Language) is a declarative language for defining, querying, modifying and controlling data in relational database systems. Declarative means you describe the desired result instead of manually specifying every physical step.\nRelational model: represents information using relations and attributes. SQL extends the mathematical model with practical features such as duplicate rows and NULL.\nSQL standard vs PostgreSQL: SQL is standardized, but PostgreSQL provides extensions such as JSONB, arrays, ranges, LATERAL, DISTINCT ON, RETURNING, row-level security and specialized indexes.\nBag/multiset semantics: SQL commonly allows duplicate rows. UNION ALL preserves duplicates; UNION removes them. Joins can multiply rows when relationships are one-to-many or many-to-many.\n\n# 2. Database environment\nDatabase: an organized collection of data managed by a database system.\nDBMS: software providing storage, queries, transactions, security, concurrency and recovery.\nRDBMS: a DBMS based primarily on relational tables, keys, constraints and relational operations.\nServer: the PostgreSQL service that accepts client connections.\nDatabase: a logical database hosted by the server.\nSchema: a namespace containing tables, views, functions, sequences and other objects.\nSession: one client connection context with its own settings and transaction state.\nExtension: packaged PostgreSQL functionality such as pg_stat_statements or specialized data types.\n\n# 3. Data modeling\nEntity: a business object represented in a data model, such as Customer or Account.\nAttribute: a property of an entity.\nRelationship: an association between entities.\nCardinality: how many instances can participate in a relationship: one-to-one, one-to-many or many-to-many.\nOptionality: whether participation is required or optional.\nERD: Entity Relationship Diagram showing entities, keys, attributes and relationships.\nLogical model: business structure independent of physical storage.\nPhysical model: concrete PostgreSQL implementation including data types, indexes, partitions and storage decisions.\nGrain: the exact meaning of one row. For example, one row per order line is different from one row per order. Grain is essential for correct aggregation.\n\n# 4. Data types\nData type defines what values a column can store and how PostgreSQL processes them.\nImportant types: integer, bigint, numeric, real, double precision, boolean, text, varchar, date, time, timestamp, timestamptz, interval, uuid, json, jsonb, arrays, ranges, enums, domains and composite values.\nNumeric precision and scale: precision limits total significant digits and scale controls decimal places. Financial values require deliberate numeric choices.\nType coercion: PostgreSQL can implicitly convert compatible values. Explicit CAST makes intent clearer and can avoid ambiguous operator behavior.\nCollation: rules used for comparing and sorting text.\nTime zone: timestamp without time zone does not represent an absolute instant; timestamptz represents an instant and displays it using the session time zone.\nInterval: represents a duration such as one day or three months. Calendar intervals are not always equivalent to a fixed number of seconds.\nUUID: identifier format useful when identifiers must be generated independently across systems.\nArray: stores multiple values in one column. Use it deliberately; a normalized child table may be better for relationships requiring independent rows.\nJSON vs JSONB: JSON preserves input text representation; JSONB stores a decomposed representation optimized for processing and indexing.\nDomain: reusable type plus constraints.\nEnum: type with a predefined set of values; useful when the set is stable.\nRange: value representing an interval such as a date or timestamp range.\n\n# 5. Keys and constraints\nCandidate key: minimal set of attributes that uniquely identifies a row.\nPrimary key: chosen candidate key used as the table identity.\nNatural key: identifier derived from business data.\nSurrogate key: generated identifier without business meaning.\nForeign key: requires a value to reference a valid key in another table.\nReferential integrity: guarantees references remain valid according to foreign-key rules.\nUNIQUE: prevents duplicate values for the constrained key.\nNOT NULL: requires a value.\nCHECK: requires a Boolean condition to hold.\nEXCLUDE: prevents conflicting rows according to an operator relationship; especially useful for non-overlapping ranges.\nDEFERRABLE constraint: allows validation to be postponed until transaction commit.\nPartial unique index: enforces uniqueness only for rows matching a predicate.\nBusiness invariant: rule that must always hold, such as one active subscription per customer.\nDatabase constraints protect correctness even when several applications write to the same database.\n\n# 6. Normalization\nFunctional dependency: if A determines B, then B functionally depends on A.\n1NF: values follow relational structure rather than uncontrolled repeating groups.\n2NF: non-key attributes do not depend on only part of a composite candidate key.\n3NF: non-key attributes do not depend transitively on another non-key attribute.\nBCNF: every determinant of a non-trivial functional dependency is a candidate key.\nDenormalization: deliberate redundancy for performance or workload simplicity.\nAnomalies: insertion, update and deletion anomalies caused by poor structure.\nNormalization improves integrity; denormalization should be deliberate, justified and measured.\n\n# 7. Query processing\nLogical query processing is different from physical execution. A simplified logical order is FROM/JOIN -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT -> ORDER BY -> LIMIT/OFFSET.\nThe optimizer may execute a physically different plan while preserving the required result.\nSELECT chooses result expressions. FROM defines source rows. WHERE filters rows. GROUP BY forms groups. HAVING filters groups. ORDER BY sorts. LIMIT/OFFSET restricts the returned portion. DISTINCT removes duplicate result rows.\nAlias: temporary name for a table or expression.\nExpression: computation producing a value.\nPredicate: expression used as a condition.\nLiteral: constant value written in SQL.\nParameter: value supplied separately from SQL text, normally through an application driver.\n\n# 8. NULL and three-valued logic\nNULL represents missing, unknown or not-applicable information depending on the model. It is not zero, false or an empty string.\nSQL predicates can be TRUE, FALSE or UNKNOWN. WHERE retains only TRUE.\nUse IS NULL and IS NOT NULL instead of equality comparison with NULL.\nImportant NULL edge cases: NOT IN, joins, aggregates, COUNT(column), NULL ordering, COALESCE and NULLIF.\n\n# 9. Operators and predicates\nComparison operators: =, <>, <, >, <=, >=.\nLogical operators: AND, OR, NOT.\nMembership: IN and NOT IN.\nExistence: EXISTS and NOT EXISTS.\nSet comparisons: ANY/SOME and ALL.\nPattern matching: LIKE and ILIKE.\nRange comparison: BETWEEN.\nPostgreSQL also provides regular-expression, JSON, array and range operators.\nAlways understand operator precedence in complex predicates.\n\n# 10. Joins\nINNER JOIN returns matching rows from both sides.\nLEFT JOIN preserves every left row and matching right rows.\nRIGHT JOIN preserves every right row.\nFULL JOIN preserves rows from both sides.\nCROSS JOIN produces the Cartesian product.\nSelf join joins a table to itself.\nLATERAL allows a right-side table expression to reference preceding FROM items.\nJoin multiplication: a one-to-many join produces multiple result rows per parent. Aggregation must respect the resulting grain.\n\n# 11. Subqueries and set operations\nSubquery: query nested inside another statement.\nCorrelated subquery: subquery referencing a value from the outer query.\nEXISTS tests whether at least one matching row exists.\nIN tests membership in a set.\nANY/SOME compares against at least one value in a set.\nALL requires a comparison against every value in a set.\nUNION combines compatible results and removes duplicates.\nUNION ALL combines results and retains duplicates.\nINTERSECT returns common rows.\nEXCEPT returns rows from the first result that are absent from the second.\n\n# 12. Aggregation\nAggregate function combines multiple rows into a result: COUNT, SUM, AVG, MIN and MAX.\nScalar function returns a value for each input row.\nFILTER restricts rows entering an aggregate.\nGROUPING SETS calculates multiple grouping levels in one statement.\nROLLUP creates hierarchical subtotals and totals.\nCUBE creates combinations of grouping dimensions.\nOrdered aggregation makes input order relevant, for example ordered string aggregation.\n\n# 13. Window functions\nWindow functions calculate across related rows without collapsing the result to one row per group.\nCore concepts: PARTITION BY, ORDER BY, window frame and named windows.\nROW_NUMBER gives unique sequence numbers.\nRANK leaves gaps after ties.\nDENSE_RANK does not leave gaps after ties.\nLAG and LEAD access previous and next rows.\nRunning SUM and moving AVG are common analytical windows.\nWindow frames determine which rows are included around the current row. ROWS, RANGE and GROUPS can have different semantics.\n\n# 14. CTEs and recursion\nCTE: Common Table Expression. It names an intermediate result inside a statement and improves decomposition and readability.\nA CTE is not automatically a performance optimization.\nRecursive CTE has an anchor query, recursive query and termination condition. It is useful for hierarchies and graph-like structures.\n\n# 15. SQL command families\nDDL defines database objects: CREATE, ALTER, DROP.\nDML changes data: INSERT, UPDATE, DELETE, MERGE.\nDQL queries data: SELECT.\nDCL controls permissions: GRANT, REVOKE.\nTCL controls transactions: COMMIT, ROLLBACK, SAVEPOINT.\n\n# 16. Data modification\nINSERT creates rows.\nUPDATE changes rows.\nDELETE removes rows.\nRETURNING lets PostgreSQL return affected rows directly.\nUPSERT inserts or resolves a uniqueness conflict using ON CONFLICT.\nMERGE conditionally performs INSERT, UPDATE or DELETE based on source/target matching.\nSafe bulk changes should first identify exact rows, inspect impact, use a transaction when appropriate, verify row counts and commit deliberately.\n\n# 17. Database objects\nImportant objects include databases, schemas, tables, indexes, sequences, identity columns, views, materialized views, functions, procedures, triggers, types, domains, extensions, temporary tables and unlogged tables.\nGenerated column: value derived from other columns by a database expression.\nTemporary table: object whose lifetime is scoped to a session or transaction depending on configuration.\nUnlogged table: reduces WAL overhead but is not appropriate for primary data that must survive crash recovery.\n\n# 18. Views\nView: stored query exposed like a virtual table. Useful for abstraction, reuse and controlled access.\nMaterialized view: stores query results physically and must be refreshed. Useful when expensive computation can be reused and slight staleness is acceptable.\n\n# 19. Functions, procedures and triggers\nFunction: reusable database logic that returns a value or set.\nProcedure: callable procedural database logic with capabilities appropriate to PostgreSQL procedures.\nTrigger: automatically invokes database logic when an event occurs.\nTrigger risks include hidden side effects, extra latency, debugging difficulty and recursive behavior.\n\n# 20. Transactions and ACID\nTransaction: logical unit of work.\nAtomicity: all-or-nothing behavior.\nConsistency: committed transactions preserve defined integrity rules.\nIsolation: concurrent work does not incorrectly interfere.\nDurability: committed changes survive the relevant failure model.\nCOMMIT completes a transaction. ROLLBACK discards uncommitted work. SAVEPOINT creates an internal rollback point.\n\n# 21. Isolation anomalies\nDirty read: reading data that another transaction has not committed.\nNon-repeatable read: the same row can return different committed values during a transaction.\nPhantom read: a repeated predicate can see a changed set of matching rows.\nLost update: concurrent writes overwrite each other's business changes.\nWrite skew: transactions each make locally valid changes that together violate a cross-row invariant.\nSerialization anomaly: concurrent execution produces a result that cannot be explained by any serial ordering.\nRead Committed generally uses statement-level snapshots. Repeatable Read provides a stable transaction snapshot with PostgreSQL-specific behavior. Serializable provides the strongest standard isolation and can require application retries.\n\n# 22. MVCC and locking\nMVCC means Multi-Version Concurrency Control. PostgreSQL keeps row versions and visibility metadata so readers and writers can often proceed concurrently.\nImportant concepts: tuple versions, snapshots, transaction IDs, visibility, dead tuples, vacuum and freezing.\nRow locks protect selected rows. Table locks protect tables according to lock mode. Blocking occurs when a session waits for a conflicting lock.\nDeadlock occurs when sessions wait in a cycle.\nAdvisory locks provide application-defined coordination.\nOptimistic concurrency detects conflicts at write time. Pessimistic concurrency locks resources before work.\nAtomic conditional UPDATE statements often prevent race conditions better than SELECT-then-UPDATE application code.\n\n# 23. Query planner and execution plans\nThe planner chooses an execution strategy using row estimates, statistics and cost models.\nCardinality estimate: expected number of rows produced by a plan node.\nSelectivity: fraction of rows expected to satisfy a condition.\nEXPLAIN shows the planned execution strategy.\nEXPLAIN ANALYZE executes the statement and reports observed execution. Be careful because write statements are actually executed.\nBad cardinality estimates can lead to bad join, scan or aggregation choices.\nExtended statistics describe relationships between columns that independent statistics cannot capture well.\n\n# 24. Scan and join algorithms\nSequential scan reads table pages sequentially and can be optimal when many rows are needed.\nIndex scan uses an index to locate rows.\nIndex-only scan can avoid heap reads when the index contains required data and visibility conditions allow it.\nBitmap scan builds a bitmap of matching table locations before fetching rows.\nNested Loop repeatedly executes an inner operation for outer rows.\nHash Join builds a hash structure and probes it.\nMerge Join processes ordered inputs together.\nNo algorithm is universally best; data volume and distribution matter.\n\n# 25. Sargability and performance\nSargability means expressing predicates so an access method such as an index can be used efficiently.\nWrapping an indexed column in a function can prevent efficient index use in many cases.\nPerformance diagnosis should use EXPLAIN rather than assumptions.\nCommon bottlenecks: bad estimates, wrong indexes, excessive rows, sorting, hashing, temporary spills, poor joins, N+1 queries, connection saturation, CPU pressure, I/O pressure and lock waits.\nwork_mem controls memory available to individual query operations such as sorts and hashes. shared_buffers is PostgreSQL shared data-page memory.\nParallel query uses workers for suitable workloads. JIT can help some expensive analytical queries but also adds compilation overhead.\n\n# 26. Index theory\nB-tree: general-purpose ordered index and common default.\nHash: specialized for equality lookups.\nGIN: useful for composite values such as JSONB, arrays and full-text search.\nGiST: generalized search tree used by many operator classes including ranges and spatial data.\nSP-GiST: specialized partitioned search structures for suitable data distributions.\nBRIN: summarizes ranges of table pages and is useful for very large naturally ordered tables.\nMulticolumn index: indexes multiple columns; column order matters.\nPartial index: indexes only rows matching a condition.\nExpression index: indexes a computed expression.\nINCLUDE/covering index: stores extra non-key columns to support index-only access.\nEvery index has storage and write-maintenance cost. Over-indexing can reduce write performance.\nConcurrent index creation can reduce blocking of normal writes but takes additional operational resources.\n\n# 27. Pagination and N+1\nOFFSET pagination becomes increasingly expensive for large offsets because earlier rows must still be located or skipped.\nKeyset pagination uses the previous page's key values to seek directly to the next page and scales better for many ordered workloads.\nCursor can mean a database cursor or an API continuation token; these are different concepts.\nN+1 occurs when an application fetches a list and then executes one query per item. Prefer joins, batching or carefully designed data access.\n\n# 28. PostgreSQL storage internals\nHeap: main table storage organized into pages.\nTuple: a row version stored in table storage.\nDead tuple: obsolete row version no longer visible to active transactions.\nWAL: Write-Ahead Log records changes before required data pages are considered safely persisted.\nCheckpoint: recovery-related process that flushes dirty data and establishes a recovery point.\nVisibility map: records page visibility properties useful to vacuum and index-only scans.\nFree-space map: tracks available space in table pages.\nTOAST: PostgreSQL mechanism for oversized field values.\nTransaction IDs are finite and freezing is required to prevent transaction ID wraparound problems.\n\n# 29. Vacuum and statistics\nVACUUM reclaims/reuses space from dead tuples and maintains visibility information.\nANALYZE collects planner statistics.\nAutovacuum automatically performs maintenance according to workload and configuration.\nBloat is inefficiently occupied storage caused by updates/deletes and storage behavior.\nLong-running transactions can prevent cleanup of old row versions.\n\n# 30. Connection pooling\nA connection pool reuses database connections and bounds the number of active connections.\nPool exhaustion can result from slow queries, leaked connections, long transactions, an undersized pool or an overloaded database.\nSimply increasing the pool can make an overloaded database worse.\n\n# 31. Prepared statements\nPrepared statements separate SQL structure from parameter values.\nThey help prevent SQL injection when parameters are bound correctly and can reduce repeated parsing.\nPostgreSQL can use generic or custom plans. Parameter distributions can make plan choice important.\n\n# 32. Security\nAuthentication proves identity. Authorization determines permitted actions.\nRoles represent identities or groups. GRANT adds privileges and REVOKE removes them.\nDefault privileges define privileges for newly created objects.\nLeast privilege means granting only what is necessary.\nRow-Level Security restricts rows a role can read or modify.\nSECURITY DEFINER runs a function with owner privileges and requires careful search_path and input handling.\nSECURITY INVOKER runs with caller privileges.\nSQL injection occurs when untrusted input changes SQL structure. Use parameterized queries.\nTLS protects network traffic. Encryption at rest protects stored data.\nSecrets such as passwords and certificates should not be hardcoded in source code.\n\n# 33. Auditing and sensitive data\nAudit trail records important security or data events. Useful fields include actor, timestamp, action, object, previous state, new state and correlation/request ID.\nData masking limits exposure of sensitive information.\nRetention rules define how long information is kept. Deletion requirements may also involve replicas, archives and backups.\n\n# 34. JSONB and full-text search\nJSONB is useful for semi-structured attributes when a fully relational model would be unnecessarily rigid.\nDo not move every relational field into JSONB. Frequently joined, constrained or filtered fields are often better as columns.\nGIN indexes can support suitable JSONB operators.\nFull-text search uses tsvector and tsquery concepts and provides ranking. It is different from simple LIKE substring search.\n\n# 35. Partitioning\nPartitioning divides one logical table into multiple physical partitions.\nCommon strategies: RANGE, LIST and HASH.\nBenefits include partition pruning, lifecycle management and smaller per-partition structures.\nCosts include more objects, operational complexity and careful partition-key design.\nPartitioning does not replace appropriate indexes.\n\n# 36. Data warehouse and analytics\nOLTP is optimized for transactional workloads. OLAP is optimized for analytical workloads.\nFact table stores measurable business events. Dimension table stores descriptive context.\nStar schema connects facts directly to dimensions. Snowflake schema further normalizes dimensions.\nGrain defines exactly what one fact row represents.\nSlowly Changing Dimensions describe strategies for tracking changing dimension attributes.\nCohort analysis groups entities by a shared starting event. Retention analysis measures continued activity over time.\n\n# 37. ETL and ELT\nETL means Extract -> Transform -> Load. ELT means Extract -> Load -> Transform.\nStaging table is an intermediate landing area.\nFull load processes the complete source dataset. Incremental load processes only changed/new data.\nWatermark records progress through an incremental source.\nLate-arriving data arrives after the expected processing window.\nDeduplication identifies repeated business events.\nData quality includes correctness, completeness, consistency, validity, uniqueness and timeliness.\nData lineage tracks where data originated and how it was transformed.\n\n# 38. Change Data Capture\nCDC identifies inserts, updates and deletes for downstream consumers.\nLogical decoding can expose PostgreSQL changes to CDC systems.\nCDC must handle ordering, duplicates, retries, offsets, failures, replay and schema evolution.\n\n# 39. Replication\nPhysical replication transfers WAL/storage-level changes.\nLogical replication transfers logical row changes through publications and subscriptions.\nRead replica is a replica used for read workloads.\nReplication lag is the difference between primary progress and replica replay.\nRead-after-write consistency requires careful routing when replicas may lag.\nReplication slots retain WAL until a consumer progresses. An abandoned slot can cause excessive WAL retention.\n\n# 40. Backup and disaster recovery\nLogical backup exports logical database objects/data.\nPhysical backup captures database storage in a recoverable physical form.\nWAL archiving stores recovery history.\nPoint-in-time recovery restores to a selected time using backups plus WAL.\nRPO is maximum acceptable data loss measured in time.\nRTO is maximum acceptable recovery time.\nHigh availability aims to keep service running through failures.\nFailover switches service to another database instance.\nA backup is not proven until restoration has been tested.\nRecovery drills validate real recovery procedures.\n\n# 41. Distributed systems\nStrong consistency provides a defined current state according to the system's consistency model.\nEventual consistency allows temporary replica differences with eventual convergence.\nTwo-phase commit coordinates distributed participants through prepare and commit but adds failure and operational complexity.\nSaga breaks distributed business work into local transactions and compensating actions.\nOutbox stores a business change and an outbound event in one local transaction before asynchronous publication.\nInbox records consumed event IDs to make duplicate delivery safe.\nIdempotent consumer produces the same intended business outcome when an event is processed more than once.\nExactly-once business effect is a practical design goal even when the transport itself is at-least-once.\n\n# 42. Schema evolution\nMigration is a controlled database structure change.\nExpand-and-contract: add compatible structure, deploy compatible code, backfill, switch usage, then remove obsolete structure later.\nBackfill populates new data from existing records.\nLarge backfills should be batched, observable, throttled when necessary and safe to retry.\nZero-downtime migration requires analysis of locks, query behavior, replication, application compatibility and rollback.\n\n# 43. Production observability\nMonitor latency, query frequency, errors, connections, waits, deadlocks, CPU, memory, I/O, disk, WAL, replication lag, vacuum health and long-running transactions.\nQuery fingerprint groups similar SQL statements for aggregate performance analysis.\nEXPLAIN ANALYZE with BUFFERS helps understand actual execution and buffer activity.\nStatement timeout and lock timeout prevent runaway work when configured appropriately.\n\n# 44. Production troubleshooting\nSlow query workflow: capture exact SQL and parameters -> measure latency -> inspect EXPLAIN ANALYZE -> compare estimated and actual rows -> inspect scans/joins -> inspect indexes -> check locks -> check CPU/I/O -> check statistics -> change one thing -> measure again -> document RCA.\nDatabase outage workflow: confirm scope -> test connectivity -> inspect server health -> check connections -> check storage -> inspect locks/long transactions -> check replication/failover -> review recent changes -> protect data integrity -> restore service -> validate applications -> perform RCA.\n\n# 45. Real-world data problems\nDuplicate-data workflow: define the business key -> identify duplicates -> choose canonical records -> clean safely -> add constraints/indexes to prevent recurrence.\nDeadlock workflow: identify transactions and lock order -> reduce transaction scope -> establish consistent resource ordering -> retry safely.\nConnection exhaustion workflow: inspect pool usage, leaks, slow queries, long transactions and database capacity before changing pool size.\n\n# 46. Temporal data\nValid time describes when a fact is true. Transaction/system time describes when the database recorded the fact.\nTemporal models should define whether periods may overlap, whether history is immutable, whether corrections are allowed and whether future-effective records exist.\nRange types and exclusion constraints can enforce non-overlapping periods.\n\n# 47. Multi-tenancy\nShared database/shared schema uses tenant_id and requires strict tenant isolation.\nShared database/separate schemas provides stronger structural separation but increases object and migration complexity.\nSeparate databases provide stronger isolation but increase operational cost.\nRLS can enforce tenant boundaries for shared-table designs.\n\n# 48. Soft delete\nSoft delete marks a row deleted rather than physically removing it, commonly with deleted_at.\nBenefits: recovery and history. Costs: query complexity, storage growth, uniqueness complexity and possible conflict with privacy deletion requirements.\n\n# 49. Hierarchical data\nAdjacency list stores parent ID and is simple to update but may require recursive queries.\nMaterialized path stores a path representation and can speed subtree queries at the cost of update complexity.\nClosure table stores ancestor-descendant relationships and can make hierarchy queries fast at the cost of extra storage.\nRecursive CTEs are a core technique for adjacency-list hierarchies.\n\n# 50. Advanced PostgreSQL topics\nExpert PostgreSQL topics include generated columns, exclusion constraints, deferrable constraints, partial/expression indexes, range/multirange types, JSONB operator classes, GIN/GiST/SP-GiST/BRIN, advisory locks, logical decoding, replication slots, publications/subscriptions, foreign data wrappers, partition-wise joins and aggregates, custom statistics targets, planner configuration and PostGIS/geospatial concepts.\n\n# 51. Planner regression\nPlans can change after data growth, statistics changes, schema changes, PostgreSQL upgrades, index changes or parameter distribution changes.\nImportant production queries should be benchmarked and their plans compared after significant changes.\n\n# 52. Security threat model\nAsk: who can connect; what can they read; what can they modify; can tenant boundaries be bypassed; can SQL injection occur; can a function escalate privileges; are secrets exposed; is traffic encrypted; is sensitive data retained unnecessarily; are security events auditable?\n\n# 53. Expert SQL review\nCorrectness: verify grain, NULL behavior, join multiplication, duplicates and constraints.\nPerformance: estimate volume, inspect the plan, validate estimates, review indexes, spills and pagination.\nConcurrency: analyze simultaneous execution, lost updates, deadlocks, locks and retries.\nSecurity: use bound parameters, least privilege and appropriate RLS; review SECURITY DEFINER carefully.\nOperations: consider cancellation, retry behavior, WAL generation, replica effects, monitoring and rollback.\n\n# 54. Expert mental model\nBusiness requirement -> business truth -> row grain -> entities and relationships -> keys and constraints -> normalization/denormalization -> transaction boundaries -> SQL -> relational correctness -> execution plan -> measurement -> concurrency -> security -> observability -> backup/recovery -> safe evolution.\n\n# 55. Definition of mastery\nA SQL concept is not complete when the learner can merely copy its syntax. Mastery means the learner can explain what it is, why it exists, when to use it, when not to use it, what happens internally, its edge cases, performance impact, concurrency behavior, security implications and production troubleshooting approach.
